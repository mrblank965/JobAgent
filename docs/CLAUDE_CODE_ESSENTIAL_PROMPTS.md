# JobAgent 团队必备 Claude Code Prompt

> 这份文档是 `CLAUDE_CODE_TEAM_GUIDE.md` 的精简操作版。  
> 使用方法：每次新开一个 Claude Code 会话，先发送一次“共同工作规则”；同一会话内后续只需发送对应的简短任务 Prompt，不需要反复粘贴全部安全规则。

## 1. 当前协作流程

```text
main（稳定、可展示版本）
  ↓ 负责人同步
feature/integration（集成与联调版本）
  ↓ 成员开始任务前同步
feature/*（各成员功能分支）
  ↓ Pull Request
feature/integration
  ↓ 全部联调与验收通过后，由负责人创建 Pull Request
main
```

| 角色 | 工作分支 | 主要职责 |
| --- | --- | --- |
| 负责人/集成 | `feature/integration` | 公共结构、接口协调、联调、最终验收 |
| 简历解析 | `feature/resume-parser` | 简历上传、解析、OCR、结构化编辑 |
| JD 解析 | `feature/jd-parser` | JD 获取、拆解和岗位信息分析 |
| 匹配分析 | `feature/match-analysis` | 简历与 JD 匹配、缺口和定制建议 |
| 结果页面 | `feature/result-page` | 结果页、投递看板、面试页面 |

每条分支都包含完整网站。成员只需要在自己的功能分支工作，不需要为每个分支分别下载一份项目。

## 2. 每次新会话首先发送：共同工作规则

把角色、分支和负责范围替换成自己的内容。同一个 Claude Code 会话只需要发送一次。

```text
你现在协助我开发 JobAgent。

我的角色是：【填写角色】
我的功能分支是：【填写功能分支】
我的负责范围是：【填写模块或目录】

开始前请阅读根目录的 AGENTS.md、README.md，以及 docs/REPOSITORY_MAP.md、docs/TEAM_WORKFLOW.md、docs/BEGINNER_TEAM_GUIDE.md 和 docs/CLAUDE_CODE_TEAM_GUIDE.md。

【明确禁止】

1. 不修改职责范围外的模块。
2. 不重写整个项目。
3. 不改变已有接口、共享类型或公共状态；如确实需要，先说明影响并等待负责人确认。
4. 不读取或修改 .env.local。
5. 不加入 API Key、真实简历或个人隐私。
6. 不安装新依赖；确实需要时，先说明依赖用途、维护情况、替代方案和将修改的锁文件。
7. 不提交、不推送、不创建 PR，完成后先等待我人工验收。
8. 不使用 reset、强制推送、删除分支或覆盖文件。

【工作顺序】

第一步：只分析现有实现，说明问题原因和最小修改方案。

第二步：列出准备修改的文件以及每个文件的作用。如果涉及公共文件，停止并等待负责人确认。

第三步：方案确认后进行最小范围修改，不顺便重构无关代码。

第四步：运行相关检查、lint、TypeScript 检查和生产构建。

第五步：检查浏览器中的正常状态、加载状态、空状态和错误状态。

第六步：向我汇报：

- 实际修改的文件；
- 每项修改的原因；
- 自动检查结果；
- 不超过 10 步的浏览器人工验收方法；
- 已知限制；
- 是否存在职责范围外的修改。

在我回复“人工验收通过”之前，不要提交或推送。

现在先检查当前分支、工作区状态和远程连接。不要修改代码。确认当前位于我的功能分支，并告诉我是否可以安全开始任务。
```

## 3. 第一次下载仓库后：找到自己的远程分支

```text
请帮我准备 JobAgent 的本地功能分支，暂时不要修改代码、提交或推送。

我的功能分支是：【填写功能分支】。

1. 确认当前文件夹是真正的 Git 仓库，不是 ZIP。
2. 确认 origin 指向 https://github.com/mrblank965/JobAgent.git。
3. 获取远程最新分支信息。
4. 确认 origin/main、origin/feature/integration 和我的远程功能分支存在。
5. 检查工作区是否有未提交修改。
6. 如果本地没有我的功能分支，在不丢失任何修改的前提下，基于远程同名分支创建本地跟踪分支。
7. 如果当前不在我的功能分支，只能在工作区干净时切换。
8. 不创建名称相近的新分支，不执行 git init、reset、强制推送或删除分支。

最后告诉我当前分支、跟踪的远程分支和工作区状态。
```

## 4. 每次开始任务前：同步最新集成版本

```text
请先不要实现功能，把 origin/feature/integration 的最新版本安全同步到我当前的功能分支。

1. 先确认当前分支和工作区状态。
2. 如果有未提交修改，立即停止，不要自动暂存、覆盖或丢弃。
3. 获取远程最新状态。
4. 使用不改写历史的方式合入 origin/feature/integration。
5. 如果发生冲突，不要自动选择任何一方；列出冲突文件、双方修改和建议找谁确认，然后等待我决定。
6. 不向 main 或 feature/integration 推送，不使用强制推送。
7. 同步后运行 lint 和 TypeScript 检查。

最后汇报同步前后版本、是否有冲突，以及现在能否开始开发。
```

## 5. 后续布置具体任务：只发送简短命令

因为共同规则已经在会话开始时发送，后续任务只需要说明任务、现象和期望。

### 5.1 新功能或优化

```text
本轮任务：【填写具体任务】。

当前情况：【填写现状或问题】。

期望结果：【填写用户操作后应该看到什么】。

请先按照共同工作规则分析现有实现，给出最小修改方案和准备修改的文件，暂时不要写代码。
```

### 5.2 确认方案并开始实现

```text
方案确认，可以开始实现。请严格按照刚才确认的范围进行最小修改；如发现必须增加文件、修改公共文件或安装依赖，先暂停并说明，不要自行扩大范围。完成后按共同工作规则检查并汇报，不要提交或推送。
```

### 5.3 修复明确的问题

```text
请修复下面的问题：

页面或功能：【填写位置】
复现步骤：【填写步骤】
实际结果：【填写看到的现象或错误原文】
期望结果：【填写正确行为】

请先定位原因并说明最小修复方案，再等待我确认。不要重构无关代码。
```

### 5.4 追加小调整

```text
请在刚才任务的原范围内追加这个调整：【填写调整内容】。

先判断是否会影响公共接口、共享类型、其他页面或已通过的测试。如果不会，请最小修改并重新运行相关检查；如果会，先停止并说明影响。
```

## 6. 实现完成后：自查与人工验收

### 6.1 让 Claude Code 自查

```text
请先不要提交或推送。按照本会话的共同工作规则，对本轮全部修改做一次严格自查。

重点确认：职责范围、计划外文件、接口和类型一致性、正常/加载/空/错误状态、隐私与敏感信息、依赖变化、lint、TypeScript 检查、相关测试和生产构建。

发现问题时做最小修复并重新检查。最后用表格汇报“检查项、结果、证据或文件、是否需要人工确认”。
```

### 6.2 让成员本人验收

```text
请保持开发服务器运行，告诉我需要打开的地址，并根据本轮任务给我一份不超过 10 步的人工验收清单。

清单需要覆盖正常操作、加载状态、空状态、至少一种错误输入、与相关页面的跳转，以及浏览器控制台是否报错。

在我回复“人工验收通过”之前，不要提交、推送或创建 PR。
```

### 6.3 运行完整项目并查看页面效果

每条功能分支都包含完整网站。成员可以在自己的功能分支运行整个项目，同时查看自己的修改和已经同步到该分支的其他模块。

```text
请在不修改代码、提交或推送的前提下，运行当前功能分支的完整项目并检查页面效果。

1. 先确认当前分支和工作区状态。
2. 检查现有依赖是否完整；不要升级依赖或擅自安装新依赖。如果确实缺少依赖，先说明缺少什么并等待我确认。
3. 启动本地开发环境。
4. 告诉我浏览器访问地址。
5. 依次检查首页、简历、JD、匹配、结果、投递看板和面试页面是否能够打开。
6. 重点检查我本轮修改的页面，同时确认公共导航、布局和其他页面没有受到影响。
7. 检查正常状态、加载状态、空状态和错误状态。
8. 检查终端和浏览器控制台是否有错误或警告。
9. 如果真实 AI 功能依赖本机环境变量，只说明该功能是否因未配置而不可用；不要读取或展示 .env.local，也不要显示任何 Key。
10. 先汇报发现的问题，不要自动扩大范围修改其他模块。

最后告诉我：

- 当前分支；
- 本地访问地址；
- 各主要页面的检查结果；
- 我的修改是否影响其他页面；
- 是否存在阻断提交的问题。
```

成员能够看到的是“当前功能分支已经包含的完整网站”。其他成员尚未合并到 `feature/integration` 的新修改不会自动出现；相关 PR 合并后，还需要重新同步 `origin/feature/integration` 才能看到。

## 7. 人工验收通过后：提交和推送

```text
人工验收已经通过。请准备提交并推送到我当前的功能分支。

1. 确认当前分支是【填写功能分支】；如果是 main 或 feature/integration，立即停止。
2. 获取远程最新状态，检查 feature/integration 在开发期间是否有新提交。
3. 如需再次同步，先安全同步；发生冲突时停止并等待确认。
4. 列出准备提交的全部文件和作用。
5. 确认没有职责范围外的修改。
6. 确认没有 .env.local、API Key、Token、真实简历、个人隐私、node_modules、.next、日志、缓存或无关大文件。
7. 再运行 lint、TypeScript 检查、相关测试和生产构建。
8. 检查 Git 提交身份；如果没有配置，停止并让我本人决定，不要编造姓名和邮箱。
9. 全部通过后创建一个内容准确的中文提交，并推送到远程同名功能分支。
10. 不向 main 或 feature/integration 直接推送，不强制推送，不删除分支。

最后告诉我提交说明、提交编号和推送结果。
```

## 8. 推送完成后：创建功能 Pull Request

功能成员的 PR 必须指向 `feature/integration`，不要直接指向 `main`。

```text
请为刚刚推送的功能分支创建或准备 Pull Request。

base：feature/integration
compare：【填写自己的功能分支】

请再次确认 base 不是 main。

PR 标题应简洁描述用户功能。PR 说明应包含：解决的问题、完成功能、主要文件、接口/类型/依赖变化、公共文件变化、自动检查结果、人工验收结果、安全检查、已知限制和下一步。

不得包含 API Key、Token、真实简历、个人隐私、.env.local 内容或电脑本地绝对路径。

如果具备 GitHub 权限，只创建 PR，不要合并，并返回链接。如果没有权限，生成完整 PR 文案并告诉我网页上如何选择 base 和 compare。不要索要密码、验证码或 Token。
```

## 9. 审核者检查功能 PR

```text
请以 JobAgent 审核者身份检查这个 Pull Request：【填写 PR 链接或编号】。

暂时不要修改代码、提交、推送或合并。

请检查：base/compare 是否正确、职责范围、无关修改、公共文件变化、接口和类型一致性、对其他模块的影响、正常/加载/空/错误状态、安全与隐私，以及 lint、TypeScript、相关测试和生产构建结果。

最后明确给出“可以合并到 feature/integration”“修改后再合并”或“暂缓合并”。如需修改，列出具体文件、原因和复现步骤。不要仅根据作者或 AI 的文字说明批准。
```

审核发现问题时，开发者继续在原功能分支修复并推送，原 PR 会自动更新，不需要重新创建分支或 PR。

## 10. 负责人开始一轮开发前：同步集成分支

当前 `main` 是稳定基线。新一轮任务开始前，由负责人先执行：

```text
请以 JobAgent 集成负责人身份，把远程最新 main 安全同步到 feature/integration。

1. 先检查当前分支、工作区和远程状态。
2. 如果有未提交修改，立即停止，不覆盖、不暂存、不丢弃。
3. 获取 origin 最新状态。
4. 切换到 feature/integration，并以不改写历史的方式同步 origin/main。
5. 如果发生冲突，不自动解决；列出冲突文件和双方修改并等待我确认。
6. 同步后运行 lint、TypeScript 检查和生产构建。
7. 检查通过后，将更新后的 feature/integration 推送到远程同名分支。
8. 不向 main 直接推送，不强制推送，不删除分支。

最后汇报同步前后版本、检查结果和成员是否可以开始同步各自分支。
```

## 11. 负责人完成一轮开发后：集成检查

```text
请以 JobAgent 集成负责人身份检查 feature/integration，暂时不要修改、提交、推送或合并。

1. 列出本轮已经合入的功能 PR 和尚未合入的 PR。
2. 检查不同模块的接口、共享类型、公共状态和页面流程是否一致。
3. 检查是否有重复实现、相互覆盖、无关修改或未确认依赖。
4. 检查敏感信息、真实简历、个人隐私和构建产物。
5. 运行完整 lint、TypeScript 检查、测试和生产构建。
6. 给出简历、JD、匹配、结果、投递和面试完整流程的人工验收清单。

最后明确给出“可以向 main 发 PR”“修复后再发 PR”或“暂缓发布”，并说明理由。不要直接合并 main。
```

## 12. 负责人创建最终 Pull Request

```text
集成检查和人工验收已经通过。请创建或准备本轮最终 Pull Request。

base：main
compare：feature/integration

确认所有计划内功能 PR 已进入 feature/integration，并确认 lint、TypeScript、测试、生产构建、完整流程验收和安全检查均已通过。

PR 说明应包含：本轮功能、来源 PR、主要结构变化、接口与依赖变化、自动检查、人工验收、安全检查、已知限制和下一轮计划。

只创建 PR，不要自动合并。返回 PR 链接，等待负责人本人或指定审核者确认。
```

## 13. PR 合并后开始下一轮

```text
我的功能 PR 已经合并到 feature/integration。请获取远程最新状态，并把 origin/feature/integration 安全同步到我当前的功能分支。

同步前先检查工作区；如果不干净就停止。不要改写历史、强制推送或自动解决冲突。同步完成后运行 lint 和 TypeScript 检查，不修改业务代码。

最后告诉我当前分支、同步结果和是否可以开始下一轮任务。
```
