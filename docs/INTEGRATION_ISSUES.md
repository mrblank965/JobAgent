## RESUME-01 · 教育经历只解析首行，专业与学历丢失

**环节**：第一步 · 简历解析

**复现步骤**

1. 准备一份教育经历为两行排版的 PDF 简历：

   ```
   海川大学 2024.09 — 2027.06
   金融学 · 硕士
   ```

2. 在简历页上传该 PDF。
3. 查看解析结果中 `education[0]`。

**实际结果**

```json
{
  "degree": "other",
  "school": "海川大学",
  "college": "",
  "major": "",
  "periodStart": "2024-09-01",
  "periodEnd": "2027-06-01",
  "performance": "GPA 3.8/4.0，排名前 10%"
}
```

`degree` 退化为 `other`（界面显示「其他」），`major` 为空。

**期望结果**

`degree` 应为「硕士」，`major` 应为「金融学」。

**根因**

`src/lib/parsers/resumeText.ts:859` 的 `buildEducationEntry(lines)` 只取 `lines[0]` 作为学校与日期的来源；紧随其后的无日期行按 `resumeText.ts:826` 注释的假设被视为「GPA 或主修课程」，不参与专业与学历抽取。

而「学校 + 日期」一行、「专业 · 学历」换行，是常见的中文简历排版，与该假设冲突。

**影响**

- 结构化画像的「专业」「学历」无法自动填充，用户必须手动补。
- `syncCommonProfile`（`src/components/resume/ResumeParserPanel.tsx:54`）依赖解析结果，因此即使点击「保存到资料库」，`major` 仍为空、`degree` 仍为「其他」。

**建议**

`buildEducationEntry` 在抽取学历与专业时把 `lines[1..]` 一并纳入候选文本，而不是仅按「无日期行 = GPA」处理。可优先在后续行中匹配学历词与专业词，匹配不到时再回落到原有逻辑。

**负责人**：简历解析（角色 B）

## RESUME-02 · 结构化画像两组字段同步时机不一致

**环节**：第一步 · 简历解析

**现象**

`src/components/resume/ResumeProfile.tsx` 的「结构化画像」区块中，同屏两组输入框行为不同：

| 字段 | 数据来源 | 生效时机 |
| --- | --- | --- |
| 姓名 / 邮箱 / 手机号 | 简历草稿 `value` | 解析后立即回填 |
| 毕业年份 / 学校 / 专业 / 学历 | 全局画像 `profile` | 需点击「保存到资料库」 |

**实际结果**

刚上传完简历时，上三个字段已自动填好，下四个仍为空，界面没有任何说明。用户容易误判为解析失败。

**期望结果**

- 至少在两组字段之间加提示，说明下半部分需点击「保存到资料库」才生效；或
- 统一两组的生效时机。

**补充说明**

该问题与 RESUME-01 叠加会放大误解。实测点击「保存到资料库」后的结果：

| 字段 | 保存后 |
| --- | --- |
| 毕业年份 | `2027` ✅ |
| 学校 | `海川大学` ✅ |
| 专业 | 仍为空 ❌ |
| 学历 | 显示「其他」 ❌ |

即：同步机制本身正常，专业与学历的缺失是由 RESUME-01 导致的，修好解析器后此项自动改善。

**非问题项**（不应误报）：目标方向、意向城市、求职类型在简历中本就没有对应信息，留空属于预期行为。

**负责人**：简历解析（角色 B）

## RESUME-03 · 技能标签把栏目名和正文粘在一起

**环节**：第一步 · 简历解析

**现象**

简历原文「专业技能」段落写的是：

```
数据工具 Python、SQL、Excel、Wind、Power BI
语言 英语六级
```

解析出的技能标签为 7 项：

```
数据工具 Python / SQL / Excel / Wind / Power BI / 语言 英语六级 / 财务报表分析
```

**问题**

- `数据工具 Python`、`语言 英语六级` 把行首的栏目小标题当成了技能内容。
- `财务报表分析` 来自教育段落的「主修课程」一行，不属于技能，被误收。
- 预期结果应是 5 项：`Python / SQL / Excel / Wind / Power BI`。

**影响**

技能标签会写进全局画像，并作为岗位匹配的唯一依据（见 MATCH-01），脏标签会一路污染到匹配结果和方向分析。

## RESUME-04 · 荣誉混入教育段落内容

**环节**：第一步 · 简历解析

**现象**

「荣誉与奖项」解析出 6 条，其中两条来自教育段落的项目符号：

```
GPA 3.7/4.0
连续三年获校级学业奖学金。
```

**说明**

「奖学金」类文字被归入荣誉符合 `resumeText.ts` 的既定规则（`HONOR_HINT`），但 `GPA 3.7/4.0` 被收进荣誉属于误判 —— 它既不是奖项，也不是荣誉称号。

**建议**

在荣誉抽取里排除形如 `GPA x.x/x.x`、纯数值或排名表达的条目，让它们留在教育段落的学业表现里。

## RESUME-05 · 实习「职位」字段为空，职位名被并入事项

**环节**：第一步 · 简历解析 → 编辑区

**现象**

原文：

```
星河证券 2025.06 — 2025.09
研究助理
– 使用 Wind 与 Excel 整理行业数据……
```

解析结果：

- 「机构或公司名称」= 星河证券 ✅
- 「职位」= 空 ❌
- 「事项」文本框 = `研究助理` + 三条正文

**问题**

1. 紧跟在公司名之后的职位行没有被识别为职位。
2. 该行被当成一条「事项」，写进了第一条要点。
3. 事项按标点被进一步切碎，例如 `使用 Wind 与 Excel 整理行业数据` 与 `协助完成新能源行业周报，累计输出 12 期` 被拆成两条。

**影响**

实习经历是简历里最核心的板块，职位为空会直接影响导出 Word、以及方向分析里「实习/工作」类证据的判定。

**负责人**：简历解析（角色 B）

## JD-01 · 简历证据列恒为空

**环节**：第二步 · JD 拆解

**现象**

JD 拆解页的「逐条技能比对」表格中，所有关键字的「简历证据」列都显示 `—`，即使简历里明明出现过对应词（简历正文含「星河证券」，JD 关键词含「证券」）。

**根因**

`src/app/jd/page.tsx:247` 与 `src/app/jd/page.tsx:267` 调用 `analyzeJD` 时，第三个参数（简历原文）写死为空字符串：

```js
analyzeJD(text, profile.skills, "")
analyzeJD(openJD.raw, profile.skills, "")
```

同一函数在岗位匹配页传的是真实原文，`src/app/match/page.tsx:39`：

```js
analyzeJD(jd.raw, profile.skills, profile.rawResume)
```

**影响**

`findEvidence(resumeText, keyword)` 拿不到原文，证据列永远为空；用户无法判断某个关键词在简历的哪一段体现过。

**建议**

改为传入 `profile.rawResume`（或 `resumeDraft.text`），与匹配页保持一致。

**负责人**：JD 解析（角色 C）

## JD-02 · 关键词含句子片段，无法比对

**环节**：第二步 · JD 拆解

**现象**

从「具备较高主动性、快递学习能力及抗压能力，能接受较长时间的工作」这类句子中，提取出的关键词包含：

```
较高主动性
能接受较长时间的工作
```

**根因**

`src/lib/jd.ts` 中「技能动词 + 短语」的兜底规则（`SKILL_VERB_PATTERN` 分支）按 `、，` 切分后只做了 2–10 字的长度过滤，没有排除句子级短语，导致整句被当成技能词。

**影响**

- 这些词几乎不可能在技能标签里命中，只会扩大「缺口」数量、压低覆盖率。
- 同样的问题出现在简历定制页的「缺口」列表和岗位匹配页的「跨岗位高频缺口」，一处产生、三处显示。

**建议**

在该分支增加过滤：命中 `的`、`能够`、`可以`、`接受` 等虚词或长度超过 6 字的短语，直接丢弃。

**负责人**：JD 解析（角色 C）

## JD-03 · 投递信息漏提取

**环节**：第二步 · JD 拆解

**现象**

JD 原文中明确写有：

```
实习地点：深圳市南山区
【申请方式】…邮件标题命名形式：【姓名-本硕学校及专业-毕业时间-计划实习月数-…】
```

解析结果：

| 字段 | 结果 |
| --- | --- |
| 城市 | `深圳市南山区`（含行政区，未规范为「深圳」） |
| 工作地点 | `—` |
| 工作时间 | `—` |
| 简历命名格式 | `—` |

**第二轮验证（前海方舟 JD）**

| 字段 | 结果 |
| --- | --- |
| 工作地点 | `深圳证券交易所广场43层` ✅（这份能提取到） |
| 工作时间 | `实习6个月，每周4天` ✅ |
| 城市 | `—` ❌（原文有「工作地点：深圳…」，仍未能归到城市字段） |
| 简历命名格式 | `—` ❌（原文「邮件标题请标注为：方舟互联实习+学校+姓名+可实习时长+一周实习几天」） |

两份 JD 都印证：工作地点与工作时间有时能提取、有时不能，而「简历命名格式」两次都为空。

**影响**

「简历命名格式」是投递时的硬性要求，漏掉会让用户按错误格式发送邮件。

## JD-05 · 岗位名称猜测错误

**环节**：第二步 · JD 拆解

**复现 JD**：前海方舟资产管理有限公司 实习招聘

**现象**

JD 原文里没有任何「岗位名称」字段，只有标题「实习招聘」。解析出的岗位名称为：

```
天或以上的实习生
```

该名称来自任职要求第 5 条「优先考虑能实习6个月或以上及每周4天或以上的实习生」，被截断后的片段。

**影响**

- JD 列表、岗位匹配页、投递看板卡片全部显示这个错误名称。
- 后续面试陪练的题目也会把这句话拼进题干：「重点说明为什么适合 前海方舟资产管理有限公司 的 天或以上的实习生」。

**第二轮验证（同一 JD，补上一行标题）**

把原文改成：

```
实习招聘
前海方舟资产管理有限公司/助理实习生
```

解析结果变为「前海方舟资产管理有限公司 · 助理实习生」✅，问题不复现。

**结论**：JD-05 只在「原文没有独立标题行、且正文里出现含『或以上 / 优先』的长句」时触发，属于兜底猜测逻辑的边界缺陷。标题行存在时正常。

**建议**

`guessJDTitle` 对候选标题做合理性校验：长度上限、排除以「或以上」「优先」「考虑」等词开头或结尾的片段；找不到合理标题时回落到原文首行，而不是截取任意片段。

**负责人**：JD 解析（角色 C）

## MATCH-01 · 覆盖率只比对技能标签，不看简历正文

**环节**：第三步 · 岗位匹配

**现象**

页面显示「当前简历画像：技能标签 7 项、简历原文 865 字」，但覆盖率 `0%`，13 个关键词全部落在「缺口」。

简历正文里明确写着「星河证券」，而 JD 关键词含「证券」，仍未算命中。

第二轮（前海方舟 JD）同样复现：页面下方「简历修改建议」写着「『证券』被 2 份 JD 要求，**画像里还没有**」，但简历原文里就有「星河证券」三个字。系统把「画像」等同于技能标签，而不是整份简历。

**根因**

`src/lib/jd.ts:339-345` 的命中判定只查 `skills`：

```js
const direct = skills.some(
  (skill) => skill === keyword || skill.includes(keyword) || keyword.includes(skill),
);
```

`resumeText` 只用于 `findEvidence` 展示证据，不参与命中判断。

**影响**

- 有相关经历但技能标签没同步的人，覆盖率会被严重低估。
- 与 JD-01 叠加后，就出现「简历里明明有，界面全说没有，连出处都不显示」的结果。

**建议**

命中判定增加一条：`resumeText` 中出现该关键词也算命中（或记为 partial），证据取 `findEvidence` 的结果。

**负责人**：匹配分析（角色 D）
