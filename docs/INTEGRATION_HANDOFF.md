## 二、feature/jd-parser · 角色 C

### JD-01 · 简历证据列恒为空

- **现象**：JD 拆解页所有关键字的「简历证据」列都显示 `—`，即使简历正文里出现过对应词。
- **位置**：`src/app/jd/page.tsx:247`、`src/app/jd/page.tsx:267`
- **原因**：调用 `analyzeJD` 时第三个参数（简历原文）写死为空字符串。
- **对照**：`src/app/match/page.tsx:39` 传的是 `profile.rawResume`，两处不一致。
- **建议**：改为传入 `profile.rawResume` 或 `resumeDraft.text`。

### JD-02 · 关键词含句子片段

- **现象**：从「具备较高主动性、快递学习能力及抗压能力，能接受较长时间的工作」中提取出关键词 `较高主动性`、`能接受较长时间的工作`。
- **位置**：`src/lib/jd.ts` SKILL_VERB_PATTERN 兜底分支
- **原因**：按 `、，` 切分后只做了 2–10 字长度过滤，未排除句子级短语。
- **影响**：三处显示（JD 拆解、岗位匹配缺口、简历定制缺口），覆盖率被稀释。
- **建议**：增加虚词与长度过滤，超过 6 字或含「的 / 能够 / 可以 / 接受」的直接丢弃。

### JD-03 · 投递信息漏提取

- **现象**：两份 JD 都提取不到「简历命名格式」；城市字段一份为空、一份为 `深圳市南山区`（未规范）。
- **位置**：`src/lib/jd.ts` `extractJDInfo`
- **证据**：原文含「邮件标题请标注为：…」，结果仍为 `—`。
- **建议**：补充对「命名形式 / 命名格式 / 邮件标题」的识别；城市做行政区后缀裁剪。

### JD-04 · 任职要求混入【申请方式】并重复

- **现象**：任职要求里出现「请将简历同时投递至 xxx@xx.com…」，且「2027年及之后毕业…」一句重复两次。
- **位置**：`src/lib/jd.ts` 分区逻辑与 `uniqueReqs`
- **建议**：先把【申请方式】段落剔除；`uniqueReqs` 增加包含关系去重。

### JD-05 · 岗位名称猜测错误

- **现象**：原文无独立标题行时，岗位名解析为 `天或以上的实习生`。
- **位置**：`src/lib/jd.ts` `guessJDTitle`
- **触发条件**：原文无标题行 **且** 正文含「或以上 / 优先」长句。
- **影响**：JD 列表、匹配页、看板卡片、面试题干全部显示错误名称。
- **建议**：对候选标题做合理性校验（长度上限、排除上述词），找不到时回落到原文首行。

### OPT-01 · 简历定制的缺口沿用伪关键词

- **说明**：数据源与 JD-02 相同，**修 JD-02 后自动消失**，无需单独改。

## 三、feature/resume-parser · 角色 B

### RESUME-01 · 教育经历只解析首行

- **现象**：`海川大学 2024.09—2027.06` + 换行 `金融学 · 硕士` 的常见排版，解析出 `degree: "other"`、`major: ""`。
- **位置**：`src/lib/parsers/resumeText.ts:859` `buildEducationEntry`
- **原因**：只取 `lines[0]`，后续无日期行被当作 GPA / 课程。
- **建议**：抽取学历与专业时把 `lines[1..]` 也纳入候选文本。

### RESUME-02 · 结构化画像两组字段同步时机不一致

- **现象**：姓名 / 邮箱 / 手机号 解析后立即回填；毕业年份 / 学校 / 专业 / 学历 需点「保存到资料库」才生效，界面无提示。
- **位置**：`src/components/resume/ResumeProfile.tsx`
- **建议**：两组之间加提示，或统一生效时机。

### RESUME-03 · 技能标签把栏目名粘在一起

- **现象**：原文「数据工具 Python、SQL…」「语言 英语六级」解析出 `数据工具 Python`、`语言 英语六级`；主修课程里的「财务报表分析」被当作技能。
- **位置**：`src/lib/parsers/resumeText.ts` 技能段落
- **影响**：技能标签写入全局画像，并作为岗位匹配的唯一依据（见 MATCH-01）。

### RESUME-04 · 荣誉混入教育段落内容

- **现象**：荣誉列表里出现 `GPA 3.7/4.0` 与 `连续三年获校级学业奖学金。`
- **位置**：`src/lib/parsers/resumeText.ts` 荣誉抽取
- **建议**：排除形如 `GPA x.x/x.x` 的纯数值或排名表达。

### RESUME-05 · 实习「职位」字段为空

- **现象**：`星河证券` 下面的 `研究助理` 没有进「职位」，而是被并入「事项」列表第一条。
- **位置**：`src/lib/parsers/resumeText.ts` 经历段落
- **影响**：导出 Word、方向分析的实习证据判定都受影响。

### RESUME-06 · 保存版本后「目标方向」不同步

- **现象**：保存简历版本为 `投研 / 资管 / 基金` 后，结构化画像的「目标方向」仍为 `— 请选择 —`。
- **位置**：`src/components/resume/ResumeParserPanel.tsx` `syncCommonProfile`
- **影响**：导出 Word 会缺这一行（`src/lib/resumeTemplate.ts:174`）；简历定制 AI 上下文缺少方向（`src/app/optimize/page.tsx:66`）。
- **建议**：保存时若「目标方向」为空则自动带入所选适用方向。

## 五、feature/integration · 角色 A

> 本节两条均为**需求**，不是缺陷，属于功能排期。

### BOARD-01 · 看板列按投递状态划分，面试入口藏得深

- **现象**：看板 6 列是「待投递 / 填写中 / 待用户处理 / 待提交确认 / 已投递 / 已结束」，招聘阶段（笔试 / 面试 / Offer）是详情里的另一个下拉。面试陪练只能在详情里改阶段才生成题目。
- **性质**：需求变更。当前实现与 `TEAM_WORKFLOW.md` 的模块划分一致。
- **方向**：按招聘阶段分列（待投递 / 已投递 / 笔试 / 面试 / Offer / 已结束），拖到「面试」列自动生成练习题。

### BOARD-02 · 缺截止日期排序与逾期提示

- **现象**：卡片按数组原顺序展示，截止日期只做文字显示，不排序、不提醒。
- **方向**：
  1. 每列内部按截止日期升序，近的在上；
  2. 未填日期的排最后；
  3. 超过今天未处理的卡片标红并显示「逾期 N 天」。
- **已确认范围**：仅列内排序 + 逾期标红，不做跨列的全局紧迫视图。

## 六、feature/result-page · 角色 E

### INTERVIEW-02 · 缺面试题库导入功能（需求）

- **现象**：练习题由 `buildInterviewGroups` 按公司名与岗位名本地生成，固定五组，无法导入自己的题库。
- **方向**：在面试陪练页提供「导入题库」入口，粘贴题目文本后自动切分并入练习。
- **已确认范围**：
  1. **全局题库**：导入一次，所有面试记录共用，不按场次拆分；
  2. **仅粘贴文本**，不做文档上传与 AI 提取（后续可扩展）；
  3. **切分规则**：按 `1.` `2.` `一、` `（1）` 等编号、换行、问号结尾切分，连续多行拼成一道题。
- **参考资料**：金融校招面试题已按「动机类 / 行为类（STAR）/ 专业类 / 情景案例类」四类整理，可直接作为首批题库。

### INTERVIEW-01 · 页面文案与实际行为不符

- **现象**：文案写「数据只在页面内存里，刷新即清空」，实测刷新后记录与答案都还在。
- **位置**：`src/app/interview/page.tsx`
- **原因**：`interviews` 已纳入 `WorkspaceSnapshot` 并持久化，文案是旧版本遗留。
- **建议**：改为「答案随打随存，自动保存在本机浏览器」。

## 七、队长 / 仓库管理

### REPO-01 · 浏览器配置目录被提交进版本库

- **现象**：`kb/.browser-profile/` 3803 个文件、约 809 MB 纳入版本控制，含 `Cookies`、`Login Data`、`History`、崩溃转储。
- **来源**：提交 `0d3ae10`「知识库」，作者 `dinghailin0615`，2026-10-31，经 PR #21 合入。
- **影响**：仓库体积由约 829 KB 增至 1.5 GB；浏览器凭据进入版本库。
- **建议**：① 加入 `.gitignore` 并取消跟踪止血；② 通知提交人检查相关账号密码；③ 是否重写历史由全组决定。

### REPO-02 · 单个提交同时删除多个共享模块

- **现象**：`0d3ae10` 一并删除 3 个 API 路由与 3 个共享 AI 模块。
- **核查**：前端无残留调用，不导致编译失败，但违反 `TEAM_WORKFLOW.md` §5「修改共享文件前先与集成人员确认」。
- **建议**：确认角色 C、D 是否知情；后续跨模块删除走 PR 说明流程。
