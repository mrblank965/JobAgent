# JobAgent Claude Code 对话式协作手册（零基础版）

> 适用对象：希望主要通过 Claude Code 对话框完成开发，而不是自己记忆大量终端命令的五名成员。  
> 配套基础手册：docs/BEGINNER_TEAM_GUIDE.md  
> 核心原则不变：main 是可演示的正式版本；每个人只在自己的功能分支开发；完成、测试并经另一名成员检查后，才通过 Pull Request 合并。

## 1. 对话式开发不等于不需要 Git

Claude Code 可以替你读取文件、修改代码、运行检查和执行 Git 操作，但仓库规则仍然存在：

- 仓库：整个 JobAgent 项目及其历史记录。
- 分支：从正式版本复制出来的个人工作台。
- 提交：某一阶段修改的版本快照。
- Pull Request：申请把功能分支合并进 main。
- main：全组都确认可以运行、可以展示的正式版本。

你可以不亲自输入每一条命令，但必须让 Claude Code说明它做了什么，并检查结果。

## 2. 五名成员使用哪条分支

| 角色 | 功能分支 | 主要任务 | 主要目录 |
| --- | --- | --- | --- |
| A 队长/集成 | feature/integration | 公共布局、数据接口、联调、部署 | src/app/layout.tsx、src/components/layout、src/types |
| B 简历解析 | feature/resume-parser | PDF/DOCX 上传、全文粘贴、文本提取、结构化与人工校对 | src/components/resume、src/app/api/parse-resume、src/lib/parsers |
| C JD 与 AI | feature/jd-parser | JD 输入、DeepSeek 调用、结构化 JD | src/components/jd、src/app/api/analyze-jd、src/lib/ai |
| D 匹配优化 | feature/match-analysis | 简历与 JD 的证据匹配、缺口和建议 | src/app/api/analyze-match、部分 src/components/analysis |
| E 结果与测试 | feature/result-page | 结果页、状态处理、演示数据和测试 | src/app/match、部分 src/components/analysis、src/data/demo |

每条分支都包含完整网站，并不是只包含一个文件夹。成员只是主要修改自己负责的目录。

## 3. 第一次打开项目后，先发这段“会话启动 Prompt”

把以下内容复制到 Claude Code 对话框，并把“我的角色”替换成自己的角色：

~~~text
你现在协助我开发 JobAgent 项目。我是第一次参加软件项目，请在每一步用中文说明你准备做什么、实际修改了哪些文件，以及我应该怎样在网页中验收。

我的角色是：成员 B，负责简历解析。
我的工作分支是：feature/resume-parser。

开始任何修改前，请先完成以下检查：
1. 阅读项目根目录的 AGENTS.md、CLAUDE.md、README.md。
2. 阅读 docs/REPOSITORY_MAP.md、docs/TEAM_WORKFLOW.md 和 docs/BEGINNER_TEAM_GUIDE.md。
3. 检查当前 Git 分支、工作区是否有未提交修改，以及远程 main 是否有新版本。
4. 如果当前不在我的工作分支，请先告诉我；在不丢失任何现有修改的前提下切换到我的分支。
5. 如果发现其他成员留下的未提交修改，不要覆盖、删除或重置，先说明情况。
6. 不读取、显示、提交或上传 .env.local 和任何 API Key。
7. 不上传真实简历、手机号、邮箱或其他个人隐私。
8. 在我明确给出本轮任务前，不修改代码。

最后请用“当前分支、工作区状态、读到的项目结构、建议的下一步”四项向我汇报。
~~~

为什么要先发这段：

- 防止在 main 上直接开发。
- 防止 Claude Code 覆盖其他成员的代码。
- 让它先理解项目，而不是重新搭一套不兼容的结构。
- 让它知道真实密钥和真实简历禁止进入仓库。

## 4. 每天开始开发时使用的 Prompt

~~~text
请帮我开始今天的开发，但先不要实现新功能。

1. 检查当前分支和未提交修改。
2. 在不丢失本地修改的前提下，获取远程 main 的最新变化。
3. 把最新 main 安全地同步到我的功能分支。
4. 如有冲突，不要自行猜测或删除代码；列出冲突文件、冲突双方的改动和建议处理方式，等我确认。
5. 检查项目依赖是否完整。
6. 启动开发环境，确认首页和我负责的页面能够打开。
7. 最后告诉我：当前分支、同步结果、页面地址、是否存在阻断问题。

不要向 main 推送，不要使用强制推送，不要删除任何分支。
~~~

如果 Claude Code 报告有未提交修改，先让它解释这些修改属于谁、是什么，再决定继续，不要直接说“全部覆盖”。

## 5. 给 Claude Code 布置任务的正确结构

一个好 Prompt 至少包含六部分：

1. 当前分支和负责范围。
2. 用户要完成什么操作。
3. 页面上应出现什么结果。
4. 数据结构和接口约束。
5. 不允许发生什么。
6. 如何测试、如何汇报。

不推荐：

~~~text
帮我把简历功能做好。
~~~

推荐：

~~~text
在 feature/resume-parser 分支完成“上传 PDF/DOCX 或粘贴简历全文并结构化”的最小功能。先阅读现有页面、类型和接口，不要重写整个项目。用户能上传带文字层的 PDF、上传 DOCX，或直接粘贴简历全文；系统提取文本并解析姓名、教育、经历、技能和优势；用户可以检查提取文本，并手动增删技能与优势。请按我给出的验收标准实现、运行 lint 和 build，并列出实际修改文件。
~~~

## 6. 完整打样：第一个任务

### 6.1 任务目标

按照现有项目计划，本轮完成以下闭环：

1. 用户进入简历解析页面。
2. 用户可以选择以下任一输入方式：
   - 上传带文字层的 PDF；
   - 上传 DOCX 格式的 Word 文件；
   - 直接粘贴简历全文。
3. 系统从 PDF/DOCX 中提取文字，并把提取结果显示出来，允许用户检查和修正。
4. 用户点击“解析简历”。
5. 系统输出姓名、教育、经历、技能和优势。
6. 用户可以手动修改姓名、教育和经历。
7. 用户可以新增或删除技能。
8. 用户可以新增或删除优势。
9. 页面刷新前，用户的修改保留在当前页面状态中。
10. 文件只在本次请求中处理，不保存到仓库、数据库或日志。
11. 不调用尚未配置的真实 DeepSeek API。
12. 暂不做 JD 匹配、账号系统和数据库。

文件边界：

- 第一版支持 PDF 和 DOCX。
- 旧版 Word 的 .doc 格式暂不支持，应提示用户另存为 .docx。
- 扫描件或纯图片 PDF 没有文字层，第一版不做 OCR，应明确提示用户改用可复制文字的 PDF、DOCX 或粘贴全文。
- 建议限制单个文件不超过 5 MB，并同时检查扩展名与 MIME 类型。
- PDF/DOCX 提取和直接粘贴最终都进入同一个 ResumeData 结构，避免后续模块区分三套数据。

### 6.3 第二个实现 Prompt：正式编写功能

~~~text
方案与必要依赖已经确认，请开始实现。严格遵守以下产品和技术要求。

【页面要求】
1. /resume 页面保留现有标题和项目风格。
2. 页面同时提供：
   - 上传 PDF/DOCX 的文件选择区；
   - “或者直接粘贴简历全文”的多行文本框。
3. 文件选择后显示文件名、类型和大小，但不要把这些信息写入服务器日志。
4. 上传并提取后，把“提取出的原始文字”显示在可编辑文本框中，让用户先检查乱码、缺行和顺序。
5. 增加“解析简历”按钮；没有文件或有效文本时按钮不可用或显示明确提示。
6. 解析或提取期间显示加载状态，避免重复点击。
7. 解析成功后展示可编辑区域：
   - 姓名：单行输入框。
   - 教育：可以编辑每一条，并能新增、删除。
   - 经历：可以编辑每一条，并能新增、删除。
   - 技能：标签形式，可以输入新增、逐个删除，重复项不重复加入。
   - 优势：标签或列表形式，可以输入新增、逐个删除，重复项不重复加入。
8. 需要有清晰的空状态、错误提示、“重新选择文件”和“重新解析”入口。
9. 对 .doc 文件提示“暂不支持旧版 Word，请另存为 .docx”。
10. 对没有文字层的扫描 PDF 提示“暂不支持扫描件 OCR，请上传可复制文字的文件或直接粘贴全文”。
11. 不要显示虚假的“AI 已分析”文案；当前应明确说明是“文档文本提取 + 本地规则演示解析”。

【支持范围与校验】
1. 支持 application/pdf 和 DOCX 对应的 MIME 类型。
2. 同时检查扩展名和 MIME；不能只相信文件名。
3. 单文件最大 5 MB。
4. 拒绝空文件、不支持的格式和同时提交多个文件。
5. 损坏或加密、无法读取的 PDF/DOCX 返回可理解的中文错误。
6. PDF 提取结果为空或极短时，按扫描件/无文字层处理。
7. 文件内容只在本次请求内存中处理，不落盘、不进数据库、不写日志。

【数据约定】
请在不破坏现有调用的前提下，把 ResumeData 调整为：
- name：可选字符串。
- education：字符串数组。
- experiences：字符串数组。
- skills：字符串数组。
- strengths：字符串数组。
如需保留未来的证书字段，可以增加 certificates 字符串数组，但不要自行增加大量暂时不用的字段。

【接口要求】
1. POST /api/parse-resume 接收 multipart/form-data。
2. 支持两种互斥输入：
   - resume：一个 PDF 或 DOCX 文件；
   - resumeText：用户粘贴或修正后的全文。
3. 至少提供一种输入；如果两种同时存在，应按清晰规则拒绝并提示用户只选择一种，避免来源不明确。
4. 文件输入先调用 src/lib/parsers/pdf.ts 或 src/lib/parsers/docx.ts 提取文字。
5. 两种入口提取/取得文字后，都调用同一个本地结构化函数生成 ResumeData。
6. 成功返回：
   {
     "resume": ResumeData,
     "extractedText": "提取或提交的文本",
     "source": "pdf | docx | pasted-text",
     "parser": "local-demo"
   }
7. 文本不是字符串、为空或少于 30 字时返回 400 和可理解的中文错误。
8. 不调用 DeepSeek。
9. 姓名不确定时返回空字符串，不要猜测。
10. 教育、经历、技能和优势只允许来自用户原文或明确词典命中，不能编造。
11. 不在服务器日志中打印文件名、简历全文或解析结果。
12. 错误响应不要包含库堆栈、服务器路径或用户文档内容。

【文档提取实现】
1. PDF 与 DOCX 的提取逻辑分别保留在 src/lib/parsers/pdf.ts 和 src/lib/parsers/docx.ts。
2. 使用适合当前 Next.js 服务端环境、维护状态明确的最小依赖。
3. 不通过外部网站或第三方转换服务上传用户文件。
4. 解析库异常要转换成统一、可理解的业务错误。
5. 提取函数只负责“文件到文字”；结构化函数只负责“文字到 ResumeData”，不要混在一起。
6. 为解析器添加至少基础的单元或可重复测试；测试文件必须是虚构、匿名且体积很小。

【本地演示结构化规则】
- 按换行清洗文本并去掉空行。
- 姓名只从开头少量行中寻找合理候选；不确定就留空。
- 识别“教育背景、教育经历、实习经历、工作经历、项目经历、技能、专业技能、自我评价、个人优势”等标题。
- 根据标题把后续行归入对应数组。
- 技能可额外使用一个小型、明确的词典从原文命中，例如 Python、Java、SQL、Excel、Tableau、Power BI、Wind、Bloomberg；只能返回原文实际出现的项目。
- 优势优先来自“个人优势、自我评价”分区；没有就返回空数组。
- 去重但保留原始顺序。

【组件结构】
请把功能拆成容易理解的小组件，不要让一个文件承担所有逻辑。可以新增：
- ResumeSourceInput：上传文件或粘贴文字。
- ExtractedTextEditor：检查和修正提取文字。
- ResumeEditor：解析结果编辑。
- EditableList：教育和经历的增删改。
- TagEditor：技能和优势的增删。
具体命名可以调整，但请说明原因。

【安全和范围】
- 不读取或修改 .env.local。
- 不加入真实 API Key。
- 不把上传文件、文件名或真实简历写入代码、测试文件、日志、数据库或 Git。
- 测试只能使用虚构、匿名化数据。
- 不修改 JD、匹配、优化和面试模块。
- 不添加账号系统或数据库。
- 除已确认的 PDF/DOCX 解析依赖外，不安装其他大型依赖。
- 不提交、不推送，完成代码和本地检查后先向我汇报。

【完成标准】
1. 实际运行项目的 lint。
2. 实际运行生产构建。
3. 使用虚构的 PDF、DOCX 和粘贴文本分别测试成功情况。
4. 测试空文本、过短文本、没有姓名、超大文件、错误格式、损坏文件和扫描版 PDF。
5. 确认上传文件与简历全文没有进入日志和 Git。
6. 汇报修改文件、每个文件作用、依赖变化、测试结果、尚未完成内容。
7. 给我一套在浏览器中逐步点击的验收方法。
~~~

### 6.5 第三个 Prompt：让 Claude Code自查和纠错

~~~text

9. 检查超大文件、.doc、错误格式、损坏文件、加密 PDF 和扫描版 PDF 的提示。
10. 搜索代码中是否存在 API Key、真实简历、手机号、邮箱，或记录文件名/简历全文的日志。
11. 检查测试文件都是虚构且体积很小，并确认没有用户文件被写入磁盘。
12. 再测试：
   - 没有姓名的文本；
   - 没有“个人优势”标题的文本；
   - 同一个技能重复出现；
   - 只有一行且不足 30 字的文本。
13. 实际运行 lint、相关测试和生产构建。

如发现问题，请直接修复后重新检查。最后用表格汇报“验收项、结果、证据或对应文件”。不要提交、不要推送。
~~~

### 6.6 第四个 Prompt：让成员亲自验收

Claude Code 的自动检查通过后，成员本人还要在浏览器操作。可以发送：

~~~text
请保持开发服务器运行，并告诉我浏览器应该打开哪个地址。

请给我一份不超过 10 步的人工验收清单。我会亲自完成：
- 上传一份虚构 PDF，检查提取文字；
- 上传一份虚构 DOCX，检查提取文字；
- 再使用粘贴全文入口；
- 修正一处提取文字并点击解析；
- 查看五类结果；
- 修改姓名；
- 修改一条教育或经历；
- 删除和新增技能；
- 删除和新增优势；
- 触发一次错误提示。

在我回复“人工验收通过”之前，不要提交或推送。
~~~

成员操作完以后，明确回复哪些通过、哪些失败。如果失败，把看到的错误原文告诉 Claude Code，让它修复后重新跑检查。

### 6.7 第五个 Prompt：提交到自己的功能分支

人工验收通过后发送：

~~~text
人工验收已经通过。请准备提交，但先做最后安全检查。

1. 确认当前分支必须是 feature/resume-parser；如果不是，立即停止。
2. 显示本次准备提交的文件清单和每个文件的作用。
3. 确认没有 .env.local、API Key、真实简历、个人隐私、node_modules 或 .next。
4. 确认没有职责范围外的意外修改。
5. 再运行一次 lint 和生产构建。
6. 如果检查全部通过，创建一次提交，提交信息使用：
   完成 PDF DOCX 简历提取与人工校对
7. 把 feature/resume-parser 推送到远程同名分支。
8. 不要合并 main，不要强制推送，不要删除分支。
9. 最后告诉我提交编号、上传结果和 GitHub 上下一步应点击的位置。
~~~

### 6.8 第六个 Prompt：创建 Pull Request

如果 Claude Code具备 GitHub 权限，可以发送：

~~~text
请为刚刚推送的 feature/resume-parser 创建一个 Pull Request。

目标分支：main
来源分支：feature/resume-parser
标题：完成 PDF DOCX 上传解析与人工校对

PR 说明必须包含：
1. 完成的用户功能。
2. 修改的主要文件。
3. 接口输入输出格式。
4. 本地规则解析的限制。
5. lint、build 和人工验收结果。
6. 使用的虚构测试数据，不得附真实简历。
7. 明确列出尚未完成：扫描件 OCR、旧版 .doc、DeepSeek 结构化解析和持久化。

只创建 PR，不要直接合并。创建完成后给我 PR 链接，并提醒我指定另一名成员检查。
~~~

如果 Claude Code没有 GitHub 写入权限，就让它生成 PR 标题和说明，然后成员到 GitHub 的 Pull requests 页面手动创建。

## 7. 审核者应该怎样和 Claude Code对话

另一名成员下载该分支后，可以发送：

~~~text
请以代码审核者身份检查 feature/resume-parser，暂时不要修改代码，也不要合并。

请与 main 比较，并重点检查：
1. 是否只实现“PDF/DOCX 上传、全文粘贴、文本提取、结构化和人工校对”。
2. 是否修改了不相关模块。
3. ResumeData、接口和前端是否一致。
4. 是否存在编造姓名、技能、经历、教育或优势的风险。
5. 是否会把简历全文或隐私写入日志、仓库或测试文件。
6. 空文本、过短文本、超大文件、错误格式、损坏文件、.doc 和扫描版 PDF 是否有中文提示。
7. 技能和优势的增删、去重是否可靠。
8. 是否存在明显的类型、样式、可访问性或安全问题。

10. 给出“可以合并”或“需要修改”的结论；需要修改时列出具体文件和复现步骤。

不要因为作者或 AI 声称测试通过就直接批准。
~~~

如果审核发现问题，开发者不要另开一条分支。继续在 feature/resume-parser 修复并推送，原 PR 会自动更新。

## 11. API Key 和隐私规则

无论使用终端还是 Claude Code，对以下规则都不能放松：

- DeepSeek Key 只放在本机 .env.local 或部署平台环境变量。
- 不把 Key 粘贴进 Prompt、截图、群聊、代码或 PR。
- 不让 Claude Code读取或展示 .env.local。
- 不上传真实简历和个人信息。
- 测试使用虚构、匿名化数据。
- 服务端日志不记录简历全文。
- AI 无法判断时返回空值、“不确定”或“未体现”，不得编造。
- 简历修改必须可追溯到用户原文。

发现密钥曾进入 GitHub 时，不能只删除文件；必须立即作废并重新生成密钥，再清理历史记录。

## 13. 常见问题

### Claude Code说完成了，就算完成了吗？

不算。必须实际运行 lint、build，并由成员本人在浏览器操作。AI 的文字汇报不是验收证据。

### Claude Code能直接在 main 修改吗？

技术上可能可以，但团队规则不允许。每次会话开始先确认分支，提交前再确认一次。

### Claude Code为什么改了很多无关文件？

通常是任务描述太宽。应要求它先给最小方案，限定目录，不允许重构无关代码，并在提交前列出文件清单。

### 功能已经推送，为什么 main 里看不到？

因为推送的是功能分支。只有 PR 审核并合并后，main 才变化。

### 每名成员需要不同仓库吗？

不需要。五个人使用同一个仓库、不同功能分支。每个人的 VS Code 和 Claude Code在自己的电脑操作同一套项目。

### 可以把简历全文或真实简历文件直接发给 Claude Code吗？

开发测试阶段不要使用真实简历，也不要把真实 PDF/DOCX 拖进 Claude Code 对话。使用本手册中的虚构样本和虚构测试文件。产品上线后，用户上传内容由网站按隐私规则在单次请求中处理，不应该被写入仓库、测试文件、数据库或日志。

## 14. 每次提交前让 Claude Code逐项确认

~~~text
请逐项回答“是/否”，任何一项不满足就不要提交：

1. 当前不是 main，而是我负责的功能分支？
2. 修改内容都属于本轮任务？
3. 没有覆盖其他成员未提交的代码？
4. 没有 .env.local、API Key 或真实个人信息？
5. 没有 node_modules、.next 或无关大文件？
6. 页面已经由我本人操作验证？
7. 空状态、错误状态和加载状态已经检查？
8. lint 已实际通过？
9. 生产构建已实际通过？
10. 提交说明能够准确描述本次功能？
11. 推送目标是当前功能分支而不是 main？
12. 下一步是创建或更新 PR，而不是直接合并？
~~~

这份手册的目标不是让成员完全不理解代码，而是让 AI 承担重复操作，让成员把注意力放在需求、边界、测试和结果判断上。每名成员都必须能够说明：用户做了什么、数据经过哪些文件、为什么结果可信、功能还有什么限制。
